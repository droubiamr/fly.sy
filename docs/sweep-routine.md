# The source sweep's instructions

The prompt of the Routine "fly.sy source sweep (06:00 and 12:00 Berlin)", which runs in its own session twice a day.
A Routine's prompt can only be changed from that session: edit this file, merge it, then ask there to "set this
routine's prompt to everything below the line in docs/sweep-routine.md on main".

---

Run the twice-daily source sweep for fly.sy now. This session is its permanent home, with the repository droubiamr/fly.sy attached and push access to it; your earlier runs and reports are above, so use them to avoid repeating news. The site answers "how do I get into Syria today": flights, land crossings and paperwork. Every fact in `data/*.json` carries a `source` (a key in `data/sources.json`), a `confidence` (verified | reported | unconfirmed), a `status` (open | caution | closed | unknown) and a `seen` date (YYYY-MM-DD, the last time the fact was re-checked). Your job is to re-check every external source the site relies on, tell the owner in plain language what has changed, post real changes from official sources to the site's News page, and keep the "last updated" time in the site footer current. The owner has asked for this sweep to push the time bump and the news items to `main` itself. The ONLY changes you may make are the `updated` field in `data/meta.json` (Step 4), new items at the top of `data/news.json` (Step 4b), and the pictures of those new items in `public/news/` (Step 4b). Do not edit any other file, do not open a PR, and do not apply the other data changes yourself.

## Step 0 — start from the live site
Work in this session's clone of the repository. If `git status --porcelain` is not empty, run `git stash -u` and mention it under Problems. Then `git fetch origin main && git checkout -B main origin/main`, so every run starts from what is live. Read `CLAUDE.md` ("Writing anything a traveller reads") before writing anything: those rules apply to every news item and to your report.

## Step 1 — load the current state
Read `data/meta.json` (`updated` is the moment shown in the site footer as "last updated", a UTC timestamp such as `2026-10-02T06:58:00Z` that each reader sees on their own clock), `data/sources.json` (the source registry; treat any source with a `url` as one to sweep, so new sources are picked up automatically), `data/entries.json` (airports and land crossings), `data/arrivals.json` (every air and land route into Syria, with airline code, origin city, entry, status, confidence, source, seen and a note that usually names flight numbers and days), `data/departures.json` (every route out of Syria, in the same shape as arrivals.json but with "to", the country it goes to, instead of "from"; each row was checked against its own source; it arrives with pull request #11, so if the file does not exist yet, skip everything about departures in this prompt), `data/airlines.json` (carriers by IATA code), `data/needs.json` (documents by mode and passport type) and `data/news.json` (the News page, newest first). Note the `seen` date on each record: anything published by a source after that date is "new".

## Step 2 — sweep each source
Outbound HTTPS goes through the environment proxy; `curl -sS -L -m 30 <url>` and the WebFetch tool both work for the sites below. Never disable TLS verification. If a site is unreachable, retry once, then record it as unreachable rather than guessing its content. Actually open every source below; do not skip any to save time.

1. **GACA, Syrian civil aviation authority** — `https://t.me/s/SyrGACA` (public web preview of the Telegram channel; posts carry `datetime="..."` attributes; page back with `?before=<post id>` until you reach posts older than the latest `seen` in entries.json; a single post is `https://t.me/SyrGACA/<id>`). `https://gaca.gov.sy/` is currently only a maintenance page. Look for: airport or airspace openings and closures, new airlines or routes licensed or started, changes at Damascus (DAM), Aleppo (ALP), Deir ez-Zor (DEZ), Latakia (LTK, closed, rehabilitation began 27 Sep 2026) and Qamishli (KAC, closed).
2. **Damascus airport official site** — `https://damairport.gov.sy`. The arrivals board is JSON at `https://damairport.gov.sy/api/flights.php` (plain GET; fields include flightNumber, airline, direction, origin, date, time; the airline list is in the same response). Read it rather than the rendered page. Some carriers are loaded weeks ahead, others typed in a day or two ahead, so a flight missing after the next two days is not proof it stopped. Compare against every `arrivals.json` row whose `entry` is `DAM`: airlines or cities that appeared or disappeared, and flight numbers/days that no longer match the row's note. The public airline list is at `/en/airlines`. Also read the departures side of the board: `https://damairport.gov.sy/api/flights.php?paged=1&dir=departure&dexact=YYYY-MM-DD&df=0` (five flights a page; add `&page=N` for the next pages). Compare it with the `departures.json` rows for Damascus in the same way you compare arrivals. An arrival is never proof of a departure, or the other way round.
3. **Aleppo airport official site** — `https://alpairport.gov.sy`, board JSON at `https://alpairport.gov.sy/api/flights.php` (same format; it usually runs only about a day ahead). Same comparison for rows whose `entry` is `ALP`. Also read its departures side at the same address as for Damascus (`https://alpairport.gov.sy/api/flights.php?paged=1&dir=departure&dexact=YYYY-MM-DD&df=0`, five flights a page, `&page=N`) and compare it with the `departures.json` rows for Aleppo; again, an arrival is never proof of a departure, or the other way round.
4. **Flight tracking** — `https://www.flightradar24.com` returns 403 to automated fetches, so use FlightAware: `https://www.flightaware.com/live/flight/<IDENT>/history`. IATA numbers mostly fail there; use the ICAO prefix: Syrian Air SYR, Fly Cham FYC, AJet TKJ, Turkish THY, Pegasus PGT, SunExpress SXS, flydubai FDB, Air Arabia ABY, Air Arabia Abu Dhabi ADY, Etihad ETD, Qatar QTR, Kuwait Airways KAC, Jazeera JZR, flynas KNE, flyadeal FAD, Saudia SVA, Royal Jordanian RJA, Dan Air DNA, LEAV Aviation NGN (e.g. `SYR444`, `FYC782`). Route finder: `https://www.flightaware.com/live/findflight?origin=<ICAO>&destination=OSDI` (OSDI Damascus, OSAP Aleppo, OSDZ Deir ez-Zor, OSLK Latakia, OSKL Qamishli). Airport sub-pages (/arrivals, /scheduled) need a login; don't try to get past it. Confirm that routes marked `verified` with source `tracker` still show flights in the last two weeks, and whether any airport marked `closed` now shows traffic. "Nothing shown" is not the same as "stopped".
5. **General Authority for Ports and Customs** — the official channel is `https://t.me/s/SyrGABC` (single post `https://t.me/SyrGABC/<id>`; search with `https://t.me/s/SyrGABC?q=<word>`). Also skim the smaller `https://t.me/s/Syrianborders`, which sometimes carries statements the main channel doesn't. Look for status or opening-hour changes at every land crossing in `entries.json`: Lebanon: Jdeidet Yabous, Al-Arida (closed since 6 Aug 2026 for bridge works, reopening announced only as "soon"), Joussieh, Jisr Qamar (Buqaia; on foot only, 06:00–18:00); Jordan: Nasib; Türkiye: Bab al-Hawa, Bab al-Salama, Al-Rai, Jarablus, Tal Abyad, Kasab (all for Syrians and Turkish citizens; watch for any change in who may cross, in either direction, into Syria and out of it; the ways out rest on the ports authority's posts of 1 January 2026, https://t.me/SyrGABC/2076, and 12 May 2026, https://t.me/SyrGABC/2966); Iraq: Abu Kamal, Semalka (24 hours from 1 Oct 2026), Al-Yarubiyah (Rabia). Also watch crossings not yet open to passengers: Dabousiyeh (Lebanon, "soon"), Al-Tanf (Iraq, freight only until road works finish), al-Hamam (Türkiye). A crossing that opens to passengers is news (Step 4b); report it for the data too.
6. **SANA, state news agency** — `https://sana.sy` (search with `https://sana.sy/?s=<term>` or the feed `https://sana.sy/search/<term>/feed/rss2/` for "معبر", "منفذ", "مطار", "تأشيرة", "الطيران"; English at `https://sana.sy/en/`). Treated as an official source, not independent press. SANA often quotes the ports authority before its Telegram channel does.
7. **EASA conflict zone bulletin** — `https://www.easa.europa.eu/en/domains/air-operations/czibs/czib-2017-03r20` and the list at `https://www.easa.europa.eu/en/domains/air-operations/czibs`. Check whether the Syria bulletin has been revised again (R21), withdrawn or extended past the validity date recorded in `sources.json` (currently "last revised 1 October 2026, valid to 30 November 2026"; R20 advises no operations over part of Syria at any height and none below FL260 over the rest — advice to operators, not a ban), and flag it when fewer than 30 days of validity remain.
8. **Lebanese General Security** — `https://www.general-security.gov.lb/ar/posts/572` (rules for Syrians entering Lebanon or crossing it into Syria; the current table is the PDF linked there, dated 24 Sep 2026). Look for a newer table or announcement.
9. **Airlines' own sites** — for each carrier in `data/airlines.json`, check the airline's newsroom or route page for announcements about Damascus, Aleppo or Deir ez-Zor (new routes, frequency changes, suspensions, winter schedules from late October). Syrian Air's own schedule is readable without login at `https://api-v2.syrlines.com/api/reservations/flights?departureAirport=<IATA>&arrivalAirport=DAM` (or `ALP`, `DEZ`) and `https://api-v2.syrlines.com/api/reservations/flight-days`. Use WebSearch with the airline name plus "Damascus" or "Syria", restricted to the last 7 days, when the site has no news page. Many airline sites block automated access; say so rather than guessing.
10. **Press and government advisories** — run WebSearch for news from the last 7 days on: "Syria airport" / "Damascus airport" / "Aleppo airport" / "Syrian airspace"; each crossing name above; "Syria visa on arrival" / "Syria e-visa"; and the Arabic equivalents ("مطار دمشق", "مطار حلب", "معبر نصيب", "معبر جديدة يابوس", "معبر العريضة", "معبر باب الهوى", "معبر سيمالكا", "تأشيرة سوريا"). Press is capped at confidence `reported`; only official bodies, the operator itself, or a checked traveller report earn `verified`.

## Step 3 — compare and decide
Say only what each source says; an advisory (EASA, a foreign travel advisory) is advice, not a ban, and airlines may still fly (Sundair, LEAV and Dan Air fly into Syria despite EASA's bulletin). Before reporting or posting anything that says "no", "never", "only", "all" or "can't", check it against `data/arrivals.json`, `data/departures.json` and `data/entries.json`; if a row contradicts it, it is wrong. Never propose turning an arrival into a departure or the other way round: each side stands on its own source.
For each finding, decide whether it changes a record in `data/`. Apply the site's rules: never propose a fact without a source; tour operators and press are capped at `reported`; a source that merely re-confirms an unchanged fact still justifies bumping that record's `seen` to today. Do not propose anything about restricted-nationality lists, military-service rules, asylum or residence effects, or expired-passport procedures unless it comes with a dated, published official source.

Classify each proposed change as URGENT or MINOR. URGENT means the published site would now mislead a traveller: an airport, crossing or route whose status should change, a route shown as flying that has stopped (a route out of Syria shown as flying that has stopped is URGENT too), or a document requirement that changed. MINOR is everything else: re-confirmations, flight-number or day corrections, confidence upgrades, a new route or crossing not yet listed, wording.

## Step 4 — update the "last updated" time in the site footer
The footer's "last updated" time is `updated` in `data/meta.json`. Pages are prerendered, so the live site only changes when a commit lands on `main` and the site rebuilds.

Move it only when the sweep was a real review. Both must hold:
- GACA, the ports authority, and at least one of the two airport sites were reachable and actually read.
- The sweep found zero URGENT changes. If it found any, a fresh time would tell travellers stale data is current. Leave it alone and say so in the report.

When both hold, set `updated` to the current UTC time to the minute, from `date -u +%Y-%m-%dT%H:%M:00Z` (for example `2026-10-02T09:52:00Z`), with a targeted replace of the old value; change nothing else in that file. Every real review moves it, the second sweep of the day included.

## Step 4b — post news
`data/news.json` feeds the site's News page. Add an item for each real-world change this sweep found that meets ALL of these:
- It was published by an official body (GACA, the ports authority, SANA, an airport's own site, a foreign government body such as Lebanese General Security, EASA) or by the operator itself (the airline's own site or channel). Never from press alone, and never a re-confirmation of something unchanged.
- Something opened, closed, started, stopped, was suspended, changed its hours, or a rule changed, or a dated future change was announced.
- It is not already in `news.json` (compare `url`, and the subject and date of the newest items).
At most 3 new items per sweep, most important first. Each item is one line in the file's existing style, inserted at the top so the file stays newest first:
`{"id":"<YYYY-MM-DD>-<short-slug>","date":"<publication date>","source":"<key in sources.json>","url":"<the exact post, article or PDF>","entries":[<entry codes it concerns, optional>],"airlines":[<IATA codes, optional>],"image":{<the picture, see below>},"title":{"ar":"...","en":"..."},"text":{"ar":"...","en":"..."}}`
The title is one short line. The text is one to three plain sentences: what changed, since when, and what a traveller should do instead if it is a closure. Say only what the source says, never a consequence it doesn't state, and re-read each sentence against `data/arrivals.json` and `data/departures.json` before pushing. Arabic in plain Modern Standard Arabic with Levantine month names (أيلول، تشرين الأول، تشرين الثاني…) and Western digits, like the existing items. Use only `source`, `entries` and `airlines` keys that already exist; add nothing to `sources.json`. News items may be posted even when Step 4 left the time alone: an urgent change is exactly what travellers need to read.

**The picture.** Give each new item the picture its source posted with the news; the site shows it as a 16:9 banner at the top of the card (a picture of another shape shows whole inside it). The script needs the repository's packages: if `node_modules` is missing, run `npm ci` once. Run `npm run news-images -- <id>` after the item is in `news.json`: it lists the pictures on the item's `url` (a Telegram post's photos and posters, or a web page's og:image) and saves each to a temp folder. Open every one (Read the files) and pick the one that shows the news itself: the crossing, the plane, the airport, the bus, or the official poster or notice. Never a portrait of an official, a meeting room or a site logo. Check that it shows the place the item is about: an album can mix several crossings or airports, so read the signs in the picture and the post's text. Then run `npm run news-images -- <id> <n>`: it writes `public/news/<id>.webp` and prints `"image":{"src":...,"width":...,"height":...,"alt":{"ar":"","en":""}}`. Put that in the item before `"title"` and fill `alt` in both languages with a few words saying what the picture shows, claiming nothing the post doesn't say. If the post has no fitting picture, or its site can't be reached, post the item without `image` and say so under Problems. Never link a picture from another site: only files in `public/news/`.

## Step 4c — check and push
If nothing changed, push nothing. Otherwise:
1. `git pull --ff-only origin main` first, then make the edits above.
2. Check: `node -e 'for (const f of ["data/meta.json","data/news.json"]) JSON.parse(require("fs").readFileSync(f,"utf8"))'` and `node --experimental-strip-types --test tests/news.test.ts tests/meta.test.ts` (it also checks that every `image` file exists and has `alt` in both languages). If a test fails, fix the item, the picture or the timestamp, or drop the item. `git status --short` must show only `data/meta.json`, `data/news.json` and the new `public/news/<id>.webp` files of this sweep's items; `git add` those pictures with the two files.
3. Commit with the message `Sweep <YYYY-MM-DD>: sources re-checked` followed by `, bump last-updated time` and/or `, <n> news item(s)` as applies, and run `git push origin HEAD:main`. If rejected because main moved, pull with `--ff-only` and retry once. On a network error, retry up to 4 times with 2s, 4s, 8s and 16s waits.
4. If the push still fails, do not force anything. Say so under Problems, with the exact error, and give the exact changes in the technical note.
Never force-push, never touch any other branch, and never commit any other file.

## Step 5 — the report
Your final message is the report. The owner reads it here in this session, and gets its headline as a phone notification (see the end of this step). They are not a developer and want to know, in simple words, what changed in the real world and whether they need to do anything. Write it in plain English, short sentences, no jargon, no JSON, no file names, no field names, no source keys, no confidence labels in the main part. Say "Damascus airport", "the Nasib crossing with Jordan", "Turkish Airlines from Istanbul", never "DAM" or "arrivals.json".

Use exactly this shape:

**Line 1, the headline.** One sentence. Either `Nothing changed today. The site is up to date.` or a count and the biggest item, for example `2 changes today. Most important: the Nasib crossing is closed.`

**What changed** — one bullet per real-world change, most important first. Each bullet is one or two plain sentences: what changed, since when, and who said so, with the link at the end. Mark urgent ones with the word `Urgent:` at the start. Leave out simple re-confirmations of things that stayed the same. Skip this section when nothing changed.

**Coming up** — one bullet per announced future change (a route starting next month, a crossing changing its hours, a bulletin about to expire), with the date and the link. Skip this section when there is nothing.

**On the News page** — one line per item you posted (its English title, and "with picture" or "no picture"), or `Nothing new was posted.`

**The site's time** — one sentence: `The "last updated" time on the site was moved to <day month, HH:MM> Berlin time.`, with the time converted from the UTC value you wrote by `TZ=Europe/Berlin date -d <that value> '+%-d %B, %H:%M'` (never the UTC digits with "Berlin" after them: 09:50 UTC is 11:50 in Berlin in summer), or `It was not moved because <plain reason>.`, or `It could not be pushed: see Problems.`

**Problems** — only if a source could not be reached, a push failed, or something looked wrong. One short bullet each. Skip this section when there were none.

Then a line with `---` and a short **Technical note** for whoever edits the data, in a smaller block: one line per change with file, record, field, old value, new value and evidence link, plus the exact lines if a push failed. Keep it under fifteen lines.

When nothing changed and the time was pushed, the whole report is three or four lines. Never invent an item you did not actually see on a source. If you could not check something, say so plainly.

Last, call the `PushNotification` tool (load it with ToolSearch if it is deferred) with `status: "proactive"` and the headline line as the message, under 200 characters, plus " Site updated." if you pushed. A "not sent" result is fine; do not retry.
